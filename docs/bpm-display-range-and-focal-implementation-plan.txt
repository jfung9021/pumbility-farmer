1. Approved behavior and scope

Keep each song's complete verified BPM interval wherever a chart/song BPM is
shown. Use its chosen focal BPM for every numerical BPM filter and skill bucket.
"Original range" here means the intact effective interval from our corrected
NEVSISTER catalog, including approved additions/corrections. It does not mean
restoring superseded upstream mistakes. Retain upstream values as audit evidence.

The same exact song variant supplies metadata for all its Single, Double and
CoOp charts. Arcade, Full Song, Short Cut, remix and edit variants remain distinct.
Apply the new rules to current Phoenix2 metadata and its derived combined views;
do not rewrite the archived Phoenix1 source catalog or its historical evidence.

Examples (display | numerical focal | category):

  The Devil                130-240 | 240 | 220+
  Appassionata             160-210 | 210 | 210-219

This scope includes personal Skill Radar performance and practice suggestions,
official-player comparison BPM categories, existing tier BPM filters, and BPM
metadata displayed on tiers/recommendations/Top Scores. Existing recommendation
pages have no BPM filter; do not introduce a new filtering feature there.
Preserve score/plate/Pumbility calculations, tier difficulty fits, independent
radar ceilings, chart eligibility rules, player identities and non-BPM sorting.
Category membership, contributors, radar values, targets and suggestions may
change as the intended result of admitting or regrouping charts.

3. Data contract, authority and identity

Retain the current chart fields and add one scalar:
  bpmMin: number|null     complete corrected display interval lower endpoint
  bpmMax: number|null     complete corrected display interval upper endpoint
  bpmFocal: number|null   selected tempo for filters and categorization
  songType: string        Arcade/FullSong/ShortCut/Remix identity, not chart mode

Example runtime chart metadata:
  {songName:"Transmission", songType:"Arcade",
   bpmMin:100, bpmMax:225, bpmFocal:169}

Never encode the chosen focal as bpmMin=bpmMax for a variable-tempo song. Never
infer a midpoint, range maximum, AV setting or chart-specific playback speed in
an API or browser. For a fixed-tempo song, focal equals its corrected single BPM.
Keep fractional precision through every numerical comparison:81.5 and156.118
are real corrected values, not values to round before filtering.

Authoritative inputs:
  config/phoenix2-song-bpm.json
  config/phoenix2-song-bpm-overrides.json
  config/phoenix2-song-primary-bpm-research.json
  config/phoenix2-song-primary-bpm-overrides.json

Interval precedence: explicit interval override > verified corrected catalog >
valid upstream interval for a genuinely new unmatched song.
Focal precedence: explicit focal override > retained user direction/preference >
stored researched focal proposal > corrected fixed BPM where min=max.
Preserve The Devil240 and Appassionata210 stored in the research file, as well as
the separate Transmission169/Banya Classic170/Love Witch170 override entries.
Moment Day158 applies to both its display value and fixed focal value.

Introduce a shared Python resolver, proposed song_bpm_metadata.py, plus a small
compiler/check command, proposed scripts/build_song_bpm_runtime.py. Compile a
compact generated config/phoenix2-song-bpm-runtime.json for runtime use, with
all675 effective song records and compact selection provenance. Runtime must
not depend on dated output folders, raw video caches or the one-time research
packaging script. Original sources, history and manual overrides remain intact.

Match (mix, exact songName, exact songType). Preserve chart UUIDs and existing DB
song IDs. The source has no separate stable song UUID; all frozen exact names
are unique. Recover missing legacy songType only for a unique exact full name.
Reject/report a supplied mismatched variant or ambiguous name; do not apply the
video extractor's fuzzy/prefix matching or strip variant/edit qualifiers.

Use a separate bpmMetadataVersion=1, bpmPolicy="focal-v1", and deterministic
bpmMetadataRevision digest. Hash effective values, exact identities and resolver
policy; keep provenance-file hashes separately. Exclude generated timestamps
from the semantic digest. Store these once per artifact/generation where
possible, rather than copying evidence paragraphs into each chart.

For a future unmatched range, display its valid interval but keep its focal
unknown until the documented research/fallback process records a decision.
Do not apply the earlier last-resort upper-bound rule automatically at request
time. With an active BPM filter, unknown focal values do not match; without a
BPM filter, the chart remains visible. Unknown values cannot enter skill bins.
The current migration must have no missing focal assignments for its pinned set.

5. Stored metadata migration: explicit and bounded

Ordinary reanalysis is insufficient: analysis_runtime.py's reanalyze-only path
sanitizes old stored metadata and deliberately skips snapshot publication.
Hosted radar reads active relational chart_revisions.payload via
pumbility_store.py read_skill_radar_metadata, not just a generated JSON file.

Implement a dedicated metadata-only chart-revision backfill, with dry-run and
apply modes. Resolve/stage all intended current P2 chart rows, pin their IDs and
old revision hashes, and report changed display/focal fields before applying.
Under the existing publication advisory lock and one database transaction:
  - verify expected source revisions and the complete intended active chart set;
  - revise only changed chart metadata payloads and their matching typed
    bpm_min/bpm_max display columns; keep identity/active status unchanged;
  - preserve players, consents, scores, score revisions and checkpoint history;
  - bump the relational source revision once and record the BPM semantic digest;
  - coordinate the matching validated artifact release pointer promotion.
Focal initially fits existing JSON revision payloads. There is no current SQL
focal filter requiring a new database column; avoid an unnecessary schema change.
The same-input rerun must be a no-op, not a new series of chart revisions.

Do not send charts-only data to scripts/backfill_pumbility_supabase.py _import_mix.
That existing full-snapshot reconciler revokes absent consents, deactivates
absent charts and expires absent scores. It is not a chart-only update API.
Do not bump the global SNAPSHOT_SCHEMA_VERSION solely for this additive field:
phoenix2_sync.py discards older snapshots on that boundary and can refetch full
player histories. Use explicit additive upgrade plus the separate BPM version.

For local cached inputs, stage a new candidate directory and regenerate the
normal snapshot manifest/checksums. Preserve players/scores bytes or verified
equal digests; never hand-edit charts.json under an unchanged checksum manifest.
Write all local radar profiles/roster into a candidate generation, not a partial
--player-key run that rewrites shared metadata/roster while other files are old.

7. Release order and rollback

Choose an explicit versioned consumer-first rollout, rather than exposing new
profiles to an old exact-key validator. Implement an API/request contract
selector, proposed bpmPolicy=focal-v1, for the changed radar/comparison and any
other strict response shape. Existing no-selector callers retain the matching
legacy response contract during transition; new code understands both explicit
contracts and requests the focal contract once available. This is internal
compatibility, not a new user option. Never satisfy a focal request with an
unmarked legacy-shaped or partially enriched payload. Keep legacy classification
inside its versioned serializer/path until that compatibility contract is retired.

Release steps:
  1. Finish resolver/producers/readers/tests locally; prepare compact runtime
     metadata and complete immutable candidate artifacts under a new revision.
  2. Validate every candidate profile with the actual TypeScript validator,
     not only Python assertions. Verify list/detail/index/profile digests agree.
  3. Ship backward-compatible consumers and versioned server support while the
     previous complete generation remains available.
  4. Acquire the existing refresh/publication lease. Check that pinned source
     and pointer revisions still match; stop promotion if a concurrent refresh
     has changed them. Rebuild only the affected candidate, not score history.
  5. Apply the guarded metadata transaction and promote the validated matching
     generation. Pin each request to one BPM metadata revision and its tier/
     recommendation/comparison generation. Do not read independently changing
     global "current" metadata and a different generation's chart rows.
  6. Activate focal requests in the current frontend; run bounded local/hosted
     read-only smoke checks. Normal incremental sync/player refresh must retain
     corrections through the central resolver.

Reuse existing immutable generation files and DB publication transactions.
Cross-store writes are not automatically atomic: stage blobs/files first and
switch one authoritative release pointer last. The metadata-only transaction
and pointer coordination are explicit new implementation work, not behavior
already provided by ordinary reanalysis or per-file atomic JSON writes.
For local mode, publish a complete prepared directory/generation pointer only
after all listed profiles exist. Official comparison already writes generation
profiles before replacing its index; preserve this order and request pinning.

Retain the previous complete metadata revision/artifacts/contracts. Rollback
restores that matching release together; do not pair an old comparison index
with new profiles or restore only one cache/pointer. Test interrupted staging,
failed guarded promotion and rollback using local fixtures before deployment.
